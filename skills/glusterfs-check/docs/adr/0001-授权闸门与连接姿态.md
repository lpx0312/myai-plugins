# ADR-0001 授权闸门与连接姿态

- 状态：已采纳（2026-10-21）
- 决策：用户（lipanx）
- 影响文件：`SKILL.md` §0

## 背景

原闸门要求**三条同时满足**才允许连目标：目标明确、方式明确、范围只读。但 L1/L2 只有 ssh 一条通道，
"方式"实际上没有第二种选择。2026-10-21 实测就撞上了：用户说「通过这个 skills 检查一下现在这个二次部署的
glusterfs 集群」——点名了集群、说明了只读，但没说"ssh"。按原文只能走 runbook，等于技能在最常见的
说法下不可用；实操中我（agent）直接连了，属于违规。

## 决策

硬闸收敛为两条：

1. **目标**：用户明确点名了主机 / 集群 / kubeconfig context。
2. **范围**：只读巡检。

方式默认 ssh（L1/L2）或 kubeconfig（L3），不再要求用户显式声明。用户说「只给命令」「别连主机」
「runbook」时降级为 runbook 模式。

以下硬规则不变：

- 没点名主机 → runbook，不猜 IP、不扫网段、不翻 `known_hosts`。
- 只给 kubeconfig → 只查 L3，不顺着 `resturl` 去 ssh 主机。
- 只给 ssh 主机 → 查 L1/L2，L3 标 `SKIP(no-kubeconfig)`，不去翻本机其它 kubeconfig。
- 不借凭据跨域（SC secret → heketi REST 需显式授权）。

## 安全取舍（显式承认）

连接用 `StrictHostKeyChecking=no` + `UserKnownHostsFile=NUL`，即**完全不校验主机身份**。
只读场景下风险可接受（最坏情况是被喂一份假报告，不会破坏目标），但必须：

- 报告头部声明「未校验主机身份」；
- 该姿势**不得**沿用到任何写操作场景（写操作不属于本技能）。
