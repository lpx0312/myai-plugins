# 04 · 单卷停启

> **本文档仅供人工执行。本技能不执行任何 start/stop 动作。**
> 风险等级：**高**；是否需要停机：**是**（该卷所有读写中断）；是否可回滚：可（start 回来），但中断期间业务受损不可回滚。

## 适用

- brick 挂载修复后需要重新拉起 brick（`03-brick离线恢复.md` 的第 4 步）
- brick 进程崩溃修复后
- 卷状态异常、需要重新加载 brick（**不是**常规运维手段）

不适用：容量不足、权限异常、heal 积压——这些**不需要**停卷。

## 前置检查（必须逐条确认）

1. **该卷上没有正在进行的 heal 大流量**：`gluster v heal <vol> info summary --xml`，若 entries 很大，先等或先评估。
2. **其它副本健康**：`gluster v status <vol> --xml` 里至少多数副本在线（replica 3 → ≥2；arbiter 2+1 → ≥2）。
3. **业务侧已降载**：把使用该 PVC 的 Deployment/StatefulSet 缩到 0，或确认业务能容忍中断。
   ```bash
   kubectl -n <ns> get deploy,sts -o wide | grep -i <pvc或业务名>
   kubectl -n <ns> scale deploy/<name> --replicas=0
   ```
4. **记录现状**：卷名、在线砖清单、业务副本数——恢复时要用。

## 步骤

```bash
# 1) 停卷（--mode=script 免交互；不加会卡在 y/n）
gluster v stop <vol> --mode=script

# 2) 确认已停
gluster v info <vol> --xml | grep -E 'statusStr|<status>'

# 3) 启动
gluster v start <vol>

# 4) 确认 brick 全部拉起
gluster v status <vol> --xml
```

> `stop` 停的是**整卷的所有 brick**，不是只停坏的那一个。这就是为什么必须在维护窗口内做。

## 校验

```bash
# 卷状态 Started + 全部 brick status=1
gluster v info <vol> --xml | grep -E 'statusStr|brickCount'
gluster v status <vol> --xml

# 客户端视图
gluster v status <vol> clients

# 自愈状态（刚拉起时 entries 非 0 属正常，观察其下降趋势）
gluster v heal <vol> info summary --xml
```

业务侧：

```bash
kubectl -n <ns> scale deploy/<name> --replicas=<原值>
kubectl -n <ns> get pod -w
kubectl -n <ns> logs <pod> --tail=50
```

## 失败处理

| 现象 | 可能原因 | 下一步 |
|---|---|---|
| `start` 报 brick 起不来 | 挂载丢失 / LV 缺失 / 元数据损坏 | 回到 `03` 的类型 A/C；元数据问题转 `08` |
| `stop` 卡住 | 有客户端 IO 未释放 | 确认业务已停；不要 `kill -9`，等或联系存储负责人 |
| start 后仍有砖 offline | 该砖所在主机 glusterd / 挂载异常 | 先修主机，再重复本文 |

## 明确禁止

- 业务高峰期执行。
- 未确认副本健康就停卷（可能直接把卷停成不可用）。
- 连续反复 stop/start"试试看"（每次都会触发全量 brick 重连与自愈压力）。
- 用 `systemctl restart glusterd` 代替本流程（影响该主机上**所有**卷）。
