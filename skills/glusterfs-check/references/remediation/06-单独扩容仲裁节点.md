# 06 · 单独扩容仲裁节点容量

> **本文档仅供人工执行。本技能不执行任何 LVM 操作。**
> 风险等级：**高**（LVM 元数据操作）；是否需要停机：不需要；是否可回滚：LVM 不可缩回，需谨慎。

## 背景

早期 StorageClass 没有加 `user.heketi.arbiter true` + `user.heketi.average-file-size 1`，导致仲裁节点按"能放下平均大小文件"分配，容量远小于数据节点。

结果：**数据节点还有空间，仲裁节点先告警/先满**。典型现象：

- 某个 PVC 的数据节点 `df` 60%、仲裁节点 90%+
- 仲裁节点上的 brick 写失败，引发该卷 `heal` 异常
- `no space left on device` 只出现在仲裁砖

先确认拓扑（`gluster v info --xml`）：`replicaCount=2, arbiterCount=1` 才是 arbiter 卷。replica-3 卷没有这个问题。

## 方案选择

| 方案 | 作用范围 | 推荐度 |
|---|---|---|
| A. 修 SC（新增 `arbiter true` + `average-file-size 1`） | **只影响新卷**，存量不变 | 首选，见 `07-SC基线修正.md` |
| B. 单独扩仲裁节点的 LV | 存量卷，逐个处理 | 存量已告警时使用（本文） |

## 前置

1. 找到仲裁节点是哪台：`gluster v info <vol> --xml` 里 `isArbiter=1` 的 brick 主机。
2. 该节点 `vgs` 有余量（`vgs -o vg_name,vg_size,vg_free`）。
3. 确认要扩的 `vg / tp / brick` 三元组，**一个都不能错**。

## 步骤

```bash
# 1) 在该仲裁节点上，定位该砖的三件套
lvs --noheadings -o lv_name,vg_name,lv_size | grep <brick_id>
# 形如：
#   tp_2be4715a...    vg_09e969e6...   5.00g
#   brick_2be4715a... vg_09e969e6...   5.00g

# 2) 先扩 thinpool
lvextend -L +1G vg_09e969e6.../tp_2be4715a...

# 3) 再扩 brick LV（-r 表示同时 resize 文件系统，必须带）
lvresize -r -L +1G /dev/vg_09e969e6.../brick_2be4715a...

# 4) 确认挂载点真的变大
df -h /var/lib/heketi/mounts/vg_09e969e6.../brick_2be4715a.../brick
lvs --noheadings -o lv_name,lv_size | grep -E 'tp_2be4715a|brick_2be4715a'

# 5) 把主机实际容量回写 heketi（在 heketi 主机执行）—— 写操作，务必确认只针对这些 vg
heketi-cli --user <u> --secret <s> device resync <vg 去掉 vg_ 前缀的 id>
```

### 顺序为什么重要（真实事故形态）

- **只扩 `tp` 不扩 `brick`**：`df` 不会变，容量等于没扩。巡检侧表现为「PCI 申请容量 / PV capacity 明显大于砖的 `df` 总量」（L1-09 对比）。
- **直接 `lvresize` 不先扩 `tp`**：`tp` 空间不够，`lvresize -r` 在 resize 文件系统阶段报 `Filesystem check failed`，LV 处于半完成状态，需要回退处理。
- 顺序固定为：**`lvextend tp` → `lvresize -r brick` → `device resync`**。

> ⚠️ 实测（2026-10-18）：`heketi-cli device resync <device-id>` **只刷新设备的 Size/Used/Free**，**不会**改砖条目里的 `Size`，也不会修正池命名。实测一台设备 resync 后 `Used 9→11 GiB`、`Free 90→88 GiB`（与 VG 实际 `88.82g` 一致），但砖仍显示 `Size (GiB): 5`，而 LV 实际是 `11.00g`。所以巡检 L1-12 判据 B 在 resync 之后**仍会报 P2**，这是正常的，不是误报。

## 脚本化处理多个卷时的要求

- 按**主机**分组执行，不要在 heketi 主机上写一个循环 ssh 一把梭。
- 每台主机执行前打印 `vg/tp/brick` 三元组并人工逐条核对（错一位就是给别的盘扩容）。
- 每扩一个，立刻 `df` 验证，再处理下一个。

## 校验

```bash
# 该卷恢复
gluster v status <vol> --xml
gluster v heal <vol> info summary --xml      # 仲裁砖的 entries 应在下降

# 容量已生效
df -h <brick 挂载点>

# thinpool 与 brick LV 尺寸应同步（差值 <10%）
lvs --noheadings -o lv_name,lv_size | grep -E 'tp_<id>|brick_<id>'
```

## 明确禁止

- **`lvresize -r` 不带 `-r`**（只改 LV 不改文件系统，`df` 不会变）。
- 只扩 `tp` 就认为完成。
- 用 `lvreduce` 缩容（必然损坏文件系统）。
- 对 replica-3 卷套用"仲裁节点"逻辑（没有仲裁砖，扩的是普通砖）。
- 扩容期间跑 `gluster v heal <vol> full`。
